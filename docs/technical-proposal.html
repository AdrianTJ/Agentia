A fast reader for Markdown and HTML artifacts

How to build it, what the research settled, what it refuted, and the one number that has to be measured before a line of production code gets written.

Target macOS 14+, Apple Silicon Stack Swift 6 · AppKit · WebKit Repo AdrianTJ/Agentia
Verified survived adversarial fact-check Judgment my engineering call, not researched Open must be measured before committing

01The recommendation

One renderer, not two

Build it

Parse Markdown with cmark-gfm in Swift, emit HTML, and render everything — Markdown and HTML alike — through a single WKWebView inside a plain AppKit window. Ship unsandboxed under Developer ID. Read-only rendering with a source toggle for v1; no Typora-style live preview.

The whole case rests on one observation: you need a web view anyway. Nothing else on macOS renders arbitrary agent-written HTML. Once WebKit is on the critical path for half your file types, adding a second native text renderer for the other half buys you nothing and costs you two theme systems, two PDF paths, and two sets of bugs.

One refinement matters, and it is where this design departs from the libraries in the wild: parse in Swift, not in the page. The popular WKWebView-based Markdown views ship markdown-it inside the HTML and hand it raw text. That puts a JavaScript engine on the first-paint path and forces JavaScript to stay switched on. Running cmark-gfm in the Swift process means the web view receives finished HTML and, for Markdown documents, can render with scripting locked down to a single pinned hash.

02What the research settled

105 agents · 23 sources · 25 claims adversarially verified · 11 killed

The useful part of this research was not what it confirmed — it was what it destroyed. Several claims I would otherwise have built on failed a three-vote refutation pass.

✓

Every shipping macOS Markdown previewer uses a C parser feeding a web view

Confirmed by reading source, not READMEs. MacDown calls hoedown_document_render into a legacy WebView; QLMarkdown pipes cmark-gfm output into webView.loadHTMLString in both the app and its Quick Look extension. No native-text-layout preview path exists in any of them.

✓

Markdown parsing is not a bottleneck and should not shape the architecture

cmark runs at 20–26 ms per megabyte — independently replicated in 2026, not just quoted. A 10 KB artifact parses in 0.17 ms; 50 KB in 0.84 ms. Any latency you feel is launch and layout, never the parser.

✓

The native-SwiftUI route has no stable landing place right now

MarkdownUI is in maintenance mode; its maintainer points new work at Textual, which is 0.5.0, macOS 15+, lays out every block eagerly with zero lazy containers, and reaches into SwiftUI privates by Mirror reflection with a separate macOS 26 branch. Fine for a hobby target, wrong for a default file handler.

✓

TextKit 2 still had open scroll and viewport defects being worked around in 2026

STTextView exists because "neither NSTextView nor TextKit 2 classes are fully functional," and its changelog shows viewport and document-height fixes landing through April 2026. Most of the radars are editing-path bugs a read-only viewer never touches — but the scroll and height class does apply.

✓

WKWebView PDF export is a supported API — the old "printing is broken" folklore is dead

createPDF(configuration:) and printOperation(with:) both went public in macOS 11. The widely cited repo demonstrating blank output was last tested on macOS 10.15 and has no commits since April 2020.

✓

The iA Writer typefaces can be bundled and shipped legally

Mono, Duo and Quattro are OFL 1.1 with dual reserved names ("iA Writer" and "Plex"). Bundling inside a commercial app is expressly permitted. Obligations: ship the license text, don't sell the fonts alone, don't reuse the reserved names on a face you modified. Subsetting for PDF embedding counts as document embedding and does not trigger renaming.

✕

Killed — "pre-warming a WKWebView cuts first load ~45%"

The benchmark everyone cites is an iPhone XR on iOS 12.2 from 2019, measuring per-load deltas inside an already-running app. That is neither the right platform nor the right measurement for macOS process cold start. Don't plan around it.

✕

Killed — "JavaScript Markdown renderers are ~7× slower than cmark"

The cited table measures library throughput on an 11 MB corpus, not the cost this architecture actually pays. It does not justify anything at artifact scale. The real reason to parse in Swift is security and JS-off rendering, not speed.

✕

Killed — "TextKit 2 is performance-neutral and production-ready as of macOS 14"

Both the "now as fast as TextKit 1" and the "ready by macOS 14" claims failed verification 0–3. Neither is safe to build on.

?

Unresolved — nothing establishes WKWebView cold-start cost on modern macOS

Every performance source examined was the wrong platform, the wrong measurement, or an unquantified author assertion. The single most important number for this project does not exist in public. It has to be measured — see §04.

Worth flagging what the research could not reach: the fan-out returned nothing verifiable on UTI registration, file watching, send-to-app mechanics, competitor pricing, notarization, or editing models. Those sections below are marked Judgment and rest on my own experience, not on cited sources.

04The launch budget

The one thing to measure before committing Open

"Lightning fast" is the requirement that decides whether this app is worth building, and it is the one the research explicitly could not answer. So the project starts with a throwaway spike whose only job is to produce a number.

The spike

// 150 lines, no app structure, one job: get a real number
func applicationWillFinishLaunching(_ n: Notification) {
  signpost("launch.begin")
  webView = WKWebView(frame: .zero, configuration: hardened())  // spawn WebContent early
  window.contentView = webView
  window.makeKeyAndOrderFront(nil)
}

func application(_ app: NSApplication, open urls: [URL]) {
  let html = Renderer.render(contentsOf: urls[0])   // cmark-gfm, sub-ms
  webView.loadHTMLString(html, baseURL: schemeBase)
}

func webView(_ w: WKWebView, didFinish _: WKNavigation!) {
  signpost("launch.firstPaint")                 // ← the number
}

Measure it from an actual Finder double-click, cold (after a reboot) and warm, on a 20 KB artifact. Three outcomes, three responses:

Cold-launch resultReadingResponse
under ~250 msComfortably viable as a default handlerProceed as proposed
250–450 msAcceptable; warm launches will feel instantProceed, then trim frameworks and defer non-essential init
over ~450 msToo slow to displace Quick LookShip a Quick Look extension for the instant peek and let the app be the deliberate open

That third branch is a genuinely good outcome rather than a failure, and it is worth building regardless. A Quick Look Preview Extension lives inside an already-resident host process, so spacebar-in-Finder is near-instant no matter what the app's cold start turns out to be. Both surfaces share one rendering framework, so it is a target in the build, not a second codebase.

Launch-path rules the design commits to now

  • AppKit lifecycle, not the SwiftUI App struct. Direct control over when the window and web view come up, and no scene machinery on the critical path.
  • SwiftUI only behind lazy instantiation. The sidebar is hidden by default — so its NSHostingView is created the first time it is shown and never during launch.
  • The HTML shell is a compiled-in string, not a bundle resource read from disk.
  • Create the web view in applicationWillFinishLaunching so WebContent process spawn overlaps file read and parse instead of following them.
  • Keep the link list short. AppKit and WebKit; nothing else loaded before first paint.

05Rendering untrusted HTML

Agent-written artifacts are code you did not review Judgment

This is the part nobody else does, and it is the reason to prefer this app over just opening the file in Safari. An HTML artifact from an agent can contain arbitrary script, phone home, or fingerprint the machine. The app renders it with the network cut at the WebKit layer and tells you what it stopped.

Concretely, the hardened configuration is:

  • A WKContentRuleList compiled once at first launch that blocks every URL except the app's own custom scheme. This is WebKit's own content-blocker engine, so it acts before the request is issued and gives an exact block count.
  • A custom WKURLSchemeHandler serving the generated HTML and any local images from the document's folder, with path traversal rejected. This avoids file:// access quirks entirely and keeps read scope explicit.
  • WKWebsiteDataStore.nonPersistent() so no cookies, storage, or cache survive between artifacts.
  • Navigation confined to the document. Clicking an external link hands it to the default browser rather than navigating the artifact away.

06PDF export

Themes are folders, not code Judgment

Use printOperation(with:) driven by a print stylesheet rather than createPDF. The print pipeline is where NSPrintInfo gives you paper size, margins and running headers, and where CSS @page and break-inside: avoid actually apply. createPDF stays as the fast path for a quick unpaginated dump. Verification confirmed both APIs are supported since macOS 11 but could not confirm the typographic quality of either — so the spike renders one code-heavy document through both and the winner takes the primary slot.

A theme is a directory, which means adding one requires no code:

Themes/Manuscript.agentiatheme/
  ├── theme.json      // name, faces, measure, scale
  ├── screen.css      // the reading view
  └── print.css       // @page, running heads, break rules

On fonts: the research settled the one genuinely risky question. iA Writer Mono, Duo and Quattro are OFL 1.1 and can be bundled in a commercial app provided the license text ships with them and the reserved names aren't reused on a modified face. IBM Plex, Inter, JetBrains Mono, Source Serif and Literata are OFL too. Charter, Palatino, SF Pro and SF Mono already ship with macOS, so several themes cost zero bundle weight. Budget roughly 4–6 MB for the bundled families.

07Becoming the default handler

UTIs, file watching, and the atomic-write trap Judgment

Registration

Declare net.daringfireball.markdown under UTImportedTypeDeclarations — imported, not exported, because you didn't define it — and reference the system public.html. Set LSHandlerRank to Alternate for both: claiming Owner for a type you don't own is bad manners and Launch Services may ignore it anyway. Then put a "Make default for .md and .html" button in settings that calls NSWorkspace.setDefaultApplication(at:toOpen:), so the user never has to do the Get Info → Change All dance.

One thing to check before writing the plist: recent macOS releases may now define a system Markdown UTI. If they do, import that instead of the Daring Fireball identifier.

Live reload, and why the obvious approach breaks

Agents almost never write in place — they write a temp file and rename it over the target. That changes the inode, so a DispatchSource watching the original file descriptor goes deaf after the first regeneration, which is exactly when you need it.

Watch the containing directory with FSEvents and kFSEventStreamCreateFlagFileEvents, filtering for the path. That survives atomic replacement, and it doubles as the folder-mode file list. Coalesce events on a ~60 ms debounce, and preserve scroll position across reloads — a live reload that throws you back to the top is worse than no live reload.

Keeping the previous contents in memory is what makes the diff view possible. cmark-gfm reports a source line for every node, so each rendered block can carry a data-sourceline attribute, and a line-level diff of the source maps directly onto blocks to highlight.

08Send to another app

Ranked by how often it will actually work Judgment

  1. Multi-representation clipboard. The highest-value item and the cheapest. Write Markdown, RTF, HTML and plain text to the pasteboard in one go; the destination picks. Paste into a terminal, get source; paste into Mail, get formatting.
  2. A real Open With menu. Enumerate installed handlers with NSWorkspace.urlsForApplications(toOpen:) and open through NSWorkspace.open(_:withApplicationAt:configuration:). Works for every app on the machine with no per-app integration.
  3. Pinned targets, file-first. For Obsidian specifically: have the user pick the vault folder once, then write the file into the vault and open it with obsidian://open?path=…. Far more robust than stuffing document content through obsidian://new?content=…, which breaks on long artifacts.
  4. The system share sheet via NSSharingServicePicker — Mail, Messages, AirDrop, Notes and any installed share extension, for free.
  5. App Intents, so Shortcuts can call "Export artifact as PDF" from a script. Small surface, high leverage for someone already automating with agents.
  6. Drag the PDF out. An NSFilePromiseProvider on the toolbar's PDF button lets you drag a rendered PDF straight into Finder or a mail composer without saving first.

09Editing, and where to stop

Read mode plus a source toggle is the right v1 Judgment

Typora-style live preview is not a feature, it's a text engine — inline rendering, caret behaviour across rendered and raw runs, selection across block boundaries, undo that spans both. It is most of a year of work and it competes directly with the app you already use for authoring. You said Obsidian owns note-taking; let it.

v1: rendered view, plus a source view you can edit and save, re-rendering on every keystroke because a sub-millisecond parse makes that free. If inline editing still appeals later, the cheap version is click-to-edit-block: click a paragraph in the rendered view, that one block swaps to a source field, commit re-renders it. Source positions from cmark-gfm make it tractable, and it delivers most of what live preview feels like for a fraction of the cost.

10Shipping

Unsandboxed, Developer ID, Sparkle Judgment

Sandboxing fights this app's core workflow. Opening a file from Finder grants access to that file, not its directory — but folder watching, folder mode, and writing into an Obsidian vault all need directory scope, which means security-scoped bookmarks and a permission prompt for every folder an agent writes to. For a tool whose entire premise is "point it at my agent's output directory," that's the wrong trade.

Ship Developer ID, hardened runtime, notarized, updated through Sparkle 2. That forgoes the Mac App Store, which is what Marked 2 and BBEdit effectively do for their power-user builds. A sandboxed App Store variant with folder features removed is possible later, but shouldn't shape v1.

12Risks

What could make this not worth finishing

Highest

WKWebView cold start blows the budget

If a Finder double-click takes half a second to paint, the app can't displace Quick Look and the premise weakens.

Mitigation: Phase 0 measures it before anything is built on top. The Quick Look extension is the fallback and is worth shipping regardless.
Medium

WebKit's PDF output isn't good enough

Verification confirmed the API works but said nothing about typographic quality — page breaks and code wrapping are unproven.

Mitigation: tested in Phase 0 on a deliberately hostile document. If both APIs disappoint, fall back to paginating in the web view with explicit page containers.
Medium

cmark-gfm parser CVEs

The library has a history of quadratic blow-up on crafted input, and this app opens files you didn't write.

Mitigation: pin a version past the fixed range, parse off the main thread with a timeout, and fail to source view rather than hanging.
Low

Scope creep into an editor

Every markdown viewer eventually grows an editor, then a file tree, then plugins — and becomes the thing you were avoiding.

Mitigation: the toolbar is capped at eight items. Anything new displaces something old.
